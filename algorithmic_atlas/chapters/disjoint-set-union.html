Связность меняется, но только в одну сторону

Представим сеть из изолированных вершин. Рёбра поступают по одному, а после каждого добавления нужно отвечать, лежат ли две вершины в одной компоненте связности. Хранить весь граф и запускать обход на каждый запрос можно, но один ответ тогда стоит $O(|V|+|E|)$. Между запросами большая часть работы повторяется.

При добавлении ребра две компоненты либо уже совпадают, либо необратимо сливаются. Внутреннее устройство компоненты для ответа не важно: нужен только устойчивый представитель. Эта потеря деталей и создаёт очень быструю структуру disjoint-set union, или union-find.

Инкрементальная динамическая связность

Поддерживается разбиение фиксированной вселенной элементов на непересекающиеся блоки. Разрешено создавать одноэлементные блоки, находить блок элемента и объединять два блока. Разделять блок, удалять ребро или восстанавливать внутренние рёбра этот интерфейс не умеет.

DSU встречается не только в графах. Та же задача возникает при вычислении классов эквивалентности, объединении пикселей в области, кластеризации, унификации имён и офлайн-обработке запросов. Общий признак — отношения только добавляются, а ответ зависит от транзитивного замыкания этих объединений.

Ранние алгоритмы эквивалентности возникали в задачах, где множество пар объявляет объекты одинаковыми, а затем требуется присвоить им единые метки. Лесное представление оказалось особенно удачным: каждое новое равенство меняет один родительский указатель, а FIND одновременно отвечает на запрос и готовит структуру к будущим запросам. История операций становится частью оптимизации.

Три операции описывают разбиение

  • MAKE-SET(x) создаёт новый блок $\{x\}$
  • FIND(x) возвращает канонического представителя блока, содержащего $x$
  • UNION(x,y) заменяет два блока их объединением, если представители различны

Клиент не должен приписывать представителю содержательный смысл. После union представителем может стать корень любого из двух деревьев. Единственная гарантия: два элемента принадлежат одному блоку тогда и только тогда, когда их FIND возвращает одинаковый идентификатор.

\[ x\sim y \quad\Longleftrightarrow\quad \operatorname{FIND}(x)=\operatorname{FIND}(y). \]

UNION обычно получает элементы, а не готовые корни: он вызывает два FIND, сравнивает результаты и связывает только различные корни. Ссылка из внутренней вершины одного дерева в другое нарушила бы правила ранга или размера и усложнила доказательство. Если корни совпадают, операция ничего не меняет.

Стоимость нужно считать на уровне обращений к памяти. MAKE-SET записывает parent и один агрегат. FIND читает по меньшей мере один parent на вершину пути и, при compression, выполняет записи. UNION после двух FIND делает постоянное число сравнений и одну связь корней. Поэтому выражение «UNION почти постоянен» включает стоимость поисков представителей; измерять только финальное присваивание некорректно.

Каждый блок представлен корневым деревом

Массив parent хранит один индекс на элемент. Корень указывает на себя; остальные вершины указывают к родителю. Несколько деревьев образуют лес, а каждое дерево в точности соответствует одному блоку разбиения.

\[ \class{atlas-notation-token notation-id-dsu-parent} {\operatorname{parent}[r]=r} \quad\text{для корня }r, \qquad \operatorname{FIND}(x)= \begin{cases} x,&\operatorname{parent}[x]=x,\\ \operatorname{FIND}(\operatorname{parent}[x]),&\text{иначе}. \end{cases} \]

Почему лес кодирует правильное разбиение

После MAKE-SET одноузловое дерево задаёт ровно $\{x\}$. UNION связывает корень одного дерева с корнем другого. Все вершины первого дерева теперь доходят до нового общего корня, как и все вершины второго; никакая вершина третьего дерева не затронута. Цикл не возникает, потому что ребро направлено между разными корнями, у которых до операции не было пути друг к другу. По индукции деревья остаются непересекающимися и точно описывают последовательность объединений.

FIND поднимается по родителям до самоссылки. Фактическая стоимость пропорциональна глубине начальной вершины и числу чтений parent. Следовательно, вся задача анализа сводится к тому, какую форму приобретают деревья и как будущие запросы могут её улучшать.

Существует и списочное представление: каждый блок хранится связным списком, а каждый элемент знает заголовок списка. FIND тогда постоянен, но при объединении нужно переназначить заголовок всем элементам присоединяемого списка. Если всегда переносить меньший список, каждый элемент меняет заголовок не более $\log_2 n$ раз и суммарная цена union равна $O(n\log n)$. Лес не переписывает всю меньшую компоненту и лучше обслуживает многочисленные FIND.

Наивное объединение может построить список

Если всегда делать второй корень родителем первого без учёта формы, последовательность $UNION(0,1)$, $UNION(1,2)$, $UNION(2,3)$ и далее способна создать цепочку. FIND с дальнего конца прочитает $n$ указателей. Формально структура остаётся корректной, но теряет преимущество перед обходом.

Корректность не ограничивает высоту

Для parent $[0,0,1,2,3,4]$ все шесть элементов имеют представителя 0. Ответы правильны, однако глубина элемента 5 равна пяти. Массив $[0,0,0,0,0,0]$ задаёт то же разбиение с глубиной один. DSU оптимизирует не математический результат FIND, а форму его доказательного пути.

Есть два независимых способа бороться с длинными путями. UNION может не создавать плохую высоту, выбирая направление связи по размеру или рангу. FIND может переписывать уже пройденный путь. Самая сильная классическая граница возникает именно от совместного действия этих решений.

Union by size: меньший блок подвешивается к большему

У каждого корня хранится число элементов его дерева. При объединении корень меньшего дерева указывает на корень большего, а новый размер равен сумме. Внутренние значения size можно не поддерживать: решение принимается только для корней.

\[ \class{atlas-notation-token notation-id-dsu-size} {\operatorname{size}[r]= |\{x:\operatorname{FIND}(x)=r\}|}. \]

Логарифмическая глубина без сжатия пути

Глубина конкретной вершины увеличивается только тогда, когда корень её дерева подвешивают к другому. По правилу размера второе дерево не меньше первого, поэтому размер компоненты этой вершины как минимум удваивается. После $k$ увеличений глубины компонент содержит не меньше $2^k$ элементов. Он не может содержать больше $n$, значит $k\le\lfloor\log_2 n\rfloor$. FIND имеет worst-case $O(\log n)$ даже без переписывания путей.

При равных размерах направление можно выбирать детерминированно, например по меньшему индексу, или произвольно. На оценку это не влияет: новое дерево вдвое больше каждого исходного. Но воспроизводимое правило облегчает тестирование и сравнение кадров.

Size остаётся точным только у действующего корня. Когда корень проигрывает union, его сохранённое число больше не описывает отдельный блок и может быть обнулено или игнорироваться. Это не мешает запросам, пока реализация сначала делает FIND и читает size результата. Ошибка появляется, если клиент хранит старый корень и использует его метаданные после последующих объединений.

Аргумент удвоения можно читать и как бюджет отдельного элемента. Запишем размеры его компоненты в моменты, когда глубина этого элемента возрастает: $s_0,s_1,\ldots$. Всегда $s_{i+1}\ge 2s_i$, независимо от операций над другими компонентами. Поэтому последовательность не длиннее $1,2,4,\ldots,2^{\lfloor\log_2 n\rfloor}$. Это доказательство не предполагает сбалансированности каждого локального поддерева и не требует, чтобы выбранный элемент был корнем. Достаточно правила, что проигрывает меньший корень. Именно поэтому произвольное разрешение равенства размеров безопасно, а присоединение большего дерева к меньшему разрушает гарантию.

Union by rank хранит верхнюю оценку высоты

Ранг корня начинается с нуля. Корень меньшего ранга подвешивается к корню большего. Если ранги равны, выбирается один корень, а его ранг увеличивается на единицу. В отличие от size, ранг не обязан совпадать с числом элементов или текущей высотой после сжатий.

\[ \class{atlas-notation-token notation-id-dsu-rank} {\operatorname{rank}[r]\leftarrow \operatorname{rank}[r]+1} \quad\text{только при связи корней равного ранга}. \]

Ранг корня не превосходит логарифм размера

Докажем, что дерево корня ранга $k$ содержит хотя бы $2^k$ элементов. Для ранга 0 это одноэлементное дерево. Новый ранг $k+1$ появляется только при соединении двух корней ранга $k$; каждое их дерево по предположению содержит не меньше $2^k$ элементов, а объединение — не меньше $2^{k+1}$. Значит, $rank(r)\le\lfloor\log_2 size(r)\rfloor$.

После path compression физическая высота может резко уменьшиться, а ранг оставляют прежним. Это безопасно: он нужен как монотонная мера истории, а не точная высота. Пересчёт рангов был бы дорогим и разрушил бы свойства, используемые амортизированным доказательством.

Между rank и size нет универсального практического победителя. Размер точнее отражает текущую массу дерева, ранг требует меньше возможных значений и исторически удобен для анализа. Оба правила гарантируют логарифмическую высоту до compression и совместимы с почти линейной амортизированной границей. Поле должно иметь одно определённое значение на всей трассе.

Из оценки $size(r)\ge 2^{rank(r)}$ следует ещё одно полезное свойство: корней высокого ранга мало. Корней ранга не меньше $k$ не может быть больше $n/2^k$, потому что их деревья не пересекаются и каждое содержит не меньше $2^k$ элементов. Амортизированный анализ использует это разрежение уровней: низких рангов много, но их быстро перепрыгивает compression; очень высокие ранги встречаются редко. Сама логарифмическая граница ещё не даёт $\alpha(n)$, однако создаёт шкалу, по которой можно безопасно начислять цену переходов FIND.

Полное сжатие пути превращает опыт запроса в shortcut

Обычный FIND только читает путь. Path compression сначала находит корень, затем делает каждую посещённую вершину непосредственным ребёнком корня. Представитель не меняется, поэтому разбиение сохраняется. Следующий FIND с любой вершины того же пути становится короче.

\[ \operatorname{FIND}(x):\quad \operatorname{parent}[x]\leftarrow \operatorname{FIND}(\operatorname{parent}[x]). \]

Корректность переписывания

Пусть исходный путь заканчивается корнем $r$. Для каждой его вершины $v$ FIND до изменения возвращает $r$. Замена ребра $v\to parent(v)$ на $v\to r$ не соединяет разные деревья, не создаёт цикл и не меняет корень. Вершины вне пути не затрагиваются. После всех замен компоненты разбиения те же, а глубина каждой переписанной вершины не больше единицы.

Рекурсивная запись коротка, но глубокий исходный путь может переполнить стек языка. Итеративный двухпроходный вариант сначала собирает путь или запоминает корень, затем проходит его снова. Можно также сжимать путь одним проходом, используя splitting или halving.

Двухпроходный FIND можно выполнить без временного массива. Первый проход находит $r$. Второй снова начинает с $x$: перед заменой parent текущей вершины запоминается старый следующий индекс, затем вершина направляется в $r$. Это постоянная дополнительная память. Старую ссылку нужно сохранить до записи, иначе обход потеряет оставшуюся часть пути.

Для точного счёта полезно разделять поиск и переписывание. На пути из $h$ рёбер первый проход читает примерно $h+1$ значений parent, второй снова читает старые ссылки и делает до $h$ записей. После этого повторный запрос к той же исходной вершине проходит одно ребро, но запрос из бокового поддерева может остаться длинным. Поэтому стоимость нельзя оценивать только по глубине последней найденной вершины. Трасса должна фиксировать, какие именно вершины посетили, какие ссылки действительно изменились и сколько будущих путей получили общий shortcut.

Path splitting и path halving переписывают на ходу

При path splitting каждая посещённая вершина начинает указывать на своего дедушку, а обход продолжается со старого родителя. В итоге переписываются почти все рёбра пути. При path halving текущая вершина тоже прыгает к дедушке, но обход продолжается уже с нового родителя; фактически сокращается примерно каждое второе ребро.

Цепочка из восьми рёбер

Полное сжатие после одного FIND делает все посещённые вершины детьми корня. Splitting заменяет указатели каждой вершины на дедушку, но некоторые новые пути пока имеют длину больше одного. Halving выполняет меньше записей в этом вызове и примерно делит путь пополам. Повторные FIND продолжают сокращение.

Эти варианты сохраняют тот же представитель, потому что дедушка лежит на исходном пути к корню. Их реальная скорость зависит от стоимости чтений и записей, компилятора и кэша. Важно не смешивать псевдокод: splitting продолжает с прежнего родителя, halving — с новым. Одна строка присваивания меняет набор переписываемых вершин.

На коротком пути полное compression может сделать меньше чтений, чем однопроходный цикл; на длинном halving уменьшает число записей. Запись дороже чтения в некоторых моделях памяти, но это нельзя предполагать без измерения. Лаборатория поэтому выводит оба счётчика и не сводит их заранее к одной «реальной» цене.

Анализ Тарьяна и ван Левена охватывает несколько одно- и двухпроходных методов. Асимптотическая оптимальность относится к точно определённым вариантам, а не к любой процедуре, случайно называющей себя «сжатием пути».

Две эвристики защищают разные моменты времени

Union by rank или size не позволяет свежим объединениям создавать высокое дерево. Path compression использует запросы, чтобы убрать уже существующие промежуточные вершины. Первая эвристика смотрит на структуру до соединения, вторая — на фактически пройденный путь.

С rank поддерживается особенно полезный инвариант: ранг строго возрастает вдоль любого родительского ребра. При связи меньший ранг указывает к большему; при равенстве ранг нового родителя сразу увеличивается. Сжатие направляет вершину к предку ещё большего ранга. Поэтому на пути нельзя долго оставаться среди одинаковых рангов.

Size даёт похожую картину через удвоения, хотя метка размера вдоль каждого ребра не обязана образовывать удобную шкалу после множества compression. В реализации достаточно выбрать одну linking-эвристику. В доказательстве важно фиксировать её заранее: утверждение о строго растущих рангах нельзя незаметно заменить рассуждением о текущей глубине, которую FIND постоянно меняет.

Эвристики нельзя анализировать как независимые константы

Rank без compression даёт логарифмическую глубину, но не обратную функцию Аккермана. Compression меняет будущие пути, а его выгода зависит от того, как деревья связывались. Граница $O(\alpha(n))$ относится к последовательности операций с совместным применением контролируемого linking и подходящего path compression.

Обратная функция Аккермана измеряет число масштабов

Функция Аккермана растёт быстрее любой фиксированной башни обычных итераций экспоненты. Её обратная спрашивает, сколько уровней такой быстрорастущей иерархии нужно, чтобы превысить $n$. Разные учебники выбирают немного разные начальные значения и двухпараметрические формы, поэтому конкретные малые ответы могут отличаться на константу. Асимптотический смысл один: рост чрезвычайно медленный.

\[ \class{atlas-notation-token notation-id-inverse-ackermann} {\alpha(n)=\min\{k:A_k(c)\ge n\}} \qquad\text{для фиксированной принятой иерархии }A_k. \]

Для любых размеров, которые можно физически разместить в памяти, распространённые определения дают значение около четырёх или ещё меньше. Но математически это не константа: на невообразимо больших аргументах функция продолжает расти. Поэтому корректная запись — $O(\alpha(n))$, а фраза «практически постоянно» описывает диапазон применения, не заменяя границу.

Число 4 зависит от определения, медленный рост — нет

Сдвиг базовых функций может дать на малом $n$ значение 3, 4 или 5. Это не опровергает теорему: варианты отличаются постоянным сдвигом. Если конкретное значение управляет ветвлением программы, нужно привести точное определение используемой $\alpha$. В оценке сложности достаточно назвать согласованную стандартную версию.

В точной теореме часто появляется двухпараметрическая $\alpha(m,n)$, зависящая от числа операций $m$ и элементов $n$. Для обычного режима $m\ge n$ удобно использовать более простое следствие: $m$ операций занимают $O(m\alpha(n))$ времени. Пространство массивов parent и rank или size равно $O(n)$.

Эта запись предполагает, что индекс, сравнение рангов и обращение к ячейке стоят константу, а элементы уже отображены в диапазон $0,\ldots,n-1$. Если исходные ключи — длинные строки, словарь, сопоставляющий их индексам, имеет собственную стоимость. DSU не превращает хеширование или сравнение внешних идентификаторов в бесплатную операцию.

Почему почти линейная сумма не следует из короткого пути

Нельзя доказать теорему, просто заявив, что «после первого FIND всё плоское». UNION позже добавляет рёбра над сжатыми вершинами, а разные запросы посещают разные пути. Нужен учёт всей последовательности. Ниже приведена схема доказательства, а не замена полного многоуровневого анализа.

Многоуровневая схема амортизированной границы

  1. Ранги корней логарифмически ограничены, а вдоль parent строго растут
  2. Диапазон рангов делится на блоки с границами, растущими по иерархии Аккермана
  3. Переход FIND в блок более высокого уровня может случиться для вершины лишь $O(\alpha(n))$ раз
  4. Переходы внутри блока оплачиваются ростом ранга целевого предка; compression заставляет будущие пути перескакивать уже оплаченные участки
  5. Суммирование начислений по вершинам и операциям даёт $O(m\alpha(n))$ в упрощённой форме

Технически трудная часть — выбрать уровни и доказать, что каждое чтение parent получает ограниченное начисление. Полное доказательство различает режимы $m$ и $n$ и конкретный вариант compression. Оно приведено в первичных работах Тарьяна, а поздний анализ Тарьяна и ван Левена сравнивает splitting и halving.

Граница амортизированная. Один FIND до переписывания может пройти $O(\log n)$ рёбер в лесе union by rank. Теорема утверждает, что длинных проходов недостаточно, чтобы большая последовательность имела логарифмичную цену на каждый запрос. Реальный счётчик чтений в лаборатории делает это различие видимым.

Зачем нужна столь быстрорастущая иерархия, а не обычные интервалы рангов? Деление рангов на равные блоки оставило бы слишком много переходов внутри каждого блока либо слишком много самих блоков. Границы Аккермана растут вложенно: следующий уровень поглощает огромное число переходов предыдущего. Когда compression меняет parent вершины на далёкого предка, её следующий платный переход либо заметно продвигается внутри текущего уровня, либо навсегда поднимает вершину на новый уровень. Первых продвижений ограниченное число на уровне, вторых — не больше $\alpha(n)$. В полном доказательстве категории зависят также от $m$; эта схема объясняет, почему результат медленнее логарифма, но всё же не константа.

Почти линейная верхняя граница не является случайностью неудачного доказательства. Для общей онлайн-задачи известны соответствующие нижние оценки в указательных моделях: нельзя заменить $\alpha$ универсальной константой и сохранить все предположения. При специальных заранее известных последовательностях возможны линейные алгоритмы, что подчёркивает роль модели доступа и знания будущего.

Краскал использует DSU как детектор цикла

Алгоритм Краскала сортирует рёбра по неубыванию веса. Перед добавлением ребра $(u,v)$ он сравнивает FIND его концов. Разные представители означают, что ребро соединяет две компоненты леса и цикла не создаёт; после выбора выполняется UNION. Одинаковый представитель означает уже существующий путь и неизбежный цикл.

Что доказывает DSU, а что доказывает жадный аргумент

Инвариант DSU доказывает только эквивалентность «один представитель — одна компонента выбранных рёбер». Из него следует корректное обнаружение цикла. Минимальность остова требует отдельного cut/exchange-доказательства: самое лёгкое допустимое ребро через разрез можно включить в некоторый оптимальный остов. Быстрая структура не заменяет доказательство жадного выбора.

\[ T_{\mathrm{Kruskal}} =O(|E|\log|E|)+O(|E|\alpha(|V|)). \]

Обычно сортировка доминирует. Если рёбра уже упорядочены или веса позволяют линейную сортировку, вклад union-find становится виднее, но всё равно остаётся почти линейным. Равные веса не ломают корректность: они могут привести к другому, но также минимальному остову.

Операционный счёт здесь особенно прозрачен. Для каждого ребра выполняются два FIND, а не более $|V|-1$ выбранных рёбер вызывают успешный UNION. Повторный UNION корней одной компоненты ничего не меняет, поэтому его можно не выполнять. Если DSU получает уже сжатые представители из двух FIND, реализация UNION не должна заново проходить исходные вершины. Такое различие констант не меняет $O(|E|\alpha(|V|))$, но делает связь между псевдокодом и реальным числом обращений к parent проверяемой.

Четыре вершины и одно отклонённое ребро

Пусть после выбора $(a,b)$ и $(b,c)$ представители $a,b,c$ совпадают, а $d$ остаётся отдельно. Ребро $(a,c)$ отклоняется как замыкающее цикл. Ребро $(c,d)$ принимается и вызывает UNION двух корней. DSU не хранит путь $a-b-c$, но равенства представителей достаточно, чтобы узнать о его существовании в выбранном лесе.

DSU забывает именно то, что нужно для удаления

После UNION структура знает, что элементы связаны, но не хранит свидетельств всех рёбер. Удаление одного ребра может не изменить компоненту или расколоть её, а по лесу представителей различить эти случаи невозможно. Обычный DSU решает incremental connectivity, не fully dynamic connectivity.

Полностью динамические алгоритмы используют другие структуры и существенно более сложный анализ. Для офлайн-задач иногда применяют rollback DSU: изменения parent и size записывают в стек и отменяют. Path compression при этом обычно отключают, потому что один FIND сделал бы много трудновосстановимых записей; union by size сохраняет логарифмическую глубину. Это другой контракт с другой сложностью.

Даже добавления требуют внимания, если вселенная элементов не фиксирована. MAKE-SET нового идентификатора расширяет массивы или словарь, и два одинаковых внешних имени не должны создать две вершины. При распределённом хранении вопрос «кто является корнем» затрагивает согласованность и обмен сообщениями. Классическая граница относится к локальной последовательной RAM-модели.

DSU также не перечисляет элементы компоненты бесплатно, не сообщает расстояния и не восстанавливает путь в исходном графе. Дополнительный агрегат можно хранить в корне и обновлять при union, если он ассоциативно объединяется. Но запрос, требующий внутренней структуры компоненты, нуждается в дополнительных данных.

Если все удаления и запросы известны заранее, время иногда можно развернуть вспять: удаление в прямом направлении станет добавлением в обратном, которое умеет обычный DSU. Более общие офлайн-схемы раскладывают интервалы жизни рёбер по дереву времени и используют rollback. Они не превращают DSU в fully dynamic структуру, а используют дополнительное знание всей последовательности.

Rollback хранит для каждого успешного UNION небольшой журнал: какой корень стал ребёнком, каким был parent, и какое значение size имел победитель. Неуспешное объединение тоже отмечается пустой записью, если клиент ожидает симметричный откат. Снимок — это длина стека; возврат к снимку восстанавливает записи в обратном порядке. Union by size оставляет FIND логарифмическим и позволяет каждой мутации занимать постоянное место в журнале. Полное path compression не «запрещено» математически, но потребовало бы записывать все переписанные рёбра и уничтожило бы этот простой контракт стоимости.

Есть и расширения без удаления. В weighted DSU ребро parent может хранить разность потенциалов до родителя, например смещение координат или паритет. FIND тогда одновременно накапливает значение вдоль пути и корректирует его при compression, а UNION проверяет согласованность нового ограничения. Это полезный шаблон, но уже не обычный интерфейс множеств: операция должна явно определить группу значений, направление разности и поведение при противоречии. Добавление одного массива без нового инварианта было бы ошибкой.

Два массива часто лучше объектов и рекурсии

Компактная реализация хранит parent и rank либо size в непрерывных массивах. Для union by size можно закодировать оба значения одним знаковым массивом: у корня отрицательный размер, у остальных индекс родителя. Это уменьшает память, но требует ясного инварианта и осторожности с типами.

Итеративный halving часто имеет короткий горячий цикл: прочитать родителя и дедушку, записать дедушку, перейти выше. Полное сжатие делает больше работы сейчас, но сильнее ускоряет ближайшие запросы. Какой вариант быстрее, зависит от числа повторных FIND, памяти и реализации. Асимптотическая эквивалентность не отменяет измерения.

Параллельный union-find требует отдельного протокола. Две нити могут одновременно связать те же корни в противоположных направлениях и создать цикл. Атомарные compare-and-swap, детерминированное правило выбора корня и анализ гонок становятся частью структуры. Простая последовательная корректность не переносится автоматически.

При сериализации следует сохранять не только parent, но и выбранный агрегат. Восстановление rank из уже сжатого леса невозможно как восстановление истории: маленькая фактическая высота не сообщает, какие равные ранги когда-то объединялись. Можно безопасно пересобрать структуру из самих блоков, но это отдельный линейный проход, а не продолжение старой трассы.

В отладочной сборке полезно проверять, что каждый индекс parent допустим, корневые ссылки самоссылочны, циклов вне корней нет, size корней суммируется в $n$, а ранг возрастает вдоль ребра. Сравнение с медленной эталонной моделью множества на малых случайных последовательностях ловит ошибки лучше отдельных красивых примеров.

Эталон может хранить явные метки компонентов и при UNION линейно перекрашивать группу. На двадцати элементах скорость не важна. После каждой случайной операции сравниваются ответы всех пар. Затем структурные счётчики отдельно подтверждают, что оптимизированная версия не только правильна, но и действительно сокращает пути.

Полезен и тест метаморфных свойств: повторный UNION внутри одной компоненты не меняет разбиение; порядок независимых объединений не меняет итоговые блоки; серия FIND не меняет ответы, хотя меняет parent. Такие проверки отделяют публичную семантику от допустимой внутренней самоорганизации.

Что чаще всего путают в union-find

  • Связывают произвольные элементы вместо двух корней
  • Увеличивают rank при неравных рангах
  • Считают rank точной текущей высотой после path compression
  • Обновляют size у проигравшего корня, а затем читают его как действующий
  • В recursive FIND возвращают корень, но забывают записать его в parent
  • Смешивают шаги splitting и halving и получают другую процедуру
  • Называют $O(\alpha(n))$ worst-case ценой каждого отдельного FIND
  • Полагают $\alpha(n)$ математической константой
  • Пытаются поддерживать удаления без дополнительной структуры
  • Считают, что DSU сам доказывает минимальность дерева Краскала

Простейший функциональный тест после каждой операции сравнивает равенство представителей со связностью в маленьком явном графе. Структурный тест отдельно проверяет лес и метаданные. Совпадение ответов ещё не гарантирует заявленную сложность: наивная цепочка тоже возвращает правильного представителя.

Лаборатория: кадры сжатия пути

Выберите длинную цепочку или ранговое дерево и сравните полное compression, splitting и halving. Каждый кадр показывает старый и новый указатель, ранги и размеры корней, глубину выбранной вершины, число чтений и записей parent. Отдельный режим UNION связывает два дерева по rank или size. Разбиение проверяется после каждого шага, поэтому геометрия не может незаметно изменить ответ FIND.

От представителя к амортизированной границе

1. Какие блоки задаёт parent $[0,0,2,2,3]$?

Показать подсказку

Дойдите от каждого индекса до самоссылочного корня.

Показать решение

Корень 0 задаёт $\{0,1\}$, корень 2 — $\{2,3,4\}$, потому что $4\to3\to2$.

2. Почему UNION должен связывать корни?

Показать подсказку

Подумайте, что случится с поддеревом внутренней вершины.

Показать решение

Связь корней объединяет целые компоненты и сохраняет дерево. Связь произвольной вершины может оторвать смысл метаданных и не подчиняется правилам rank/size.

3. Докажите завершимость FIND в корректном лесу.

Показать подсказку

Используйте конечность и отсутствие циклов кроме самоссылки корня.

Показать решение

Каждый шаг идёт к строгому предку. В конечном ациклическом дереве нельзя посещать вершину повторно, поэтому путь заканчивается единственной самоссылкой корня.

4. Почему union by size ограничивает глубину логарифмом?

Показать подсказку

Посчитайте размер компоненты после каждого увеличения глубины элемента.

Показать решение

Каждое увеличение глубины происходит при присоединении к не меньшему дереву, поэтому размер компоненты как минимум удваивается. Удвоений не больше $\log_2 n$.

5. Когда увеличивается rank?

Показать подсказку

Разберите отдельно равные и неравные ранги корней.

Показать решение

Только при связи двух корней равного ранга; победивший корень получает ранг на единицу больше. При неравных рангах больший не меняется.

6. Почему rank не уменьшают после path compression?

Показать подсказку

Ранг — историческая мера для решения UNION, а не измерение текущей высоты.

Показать решение

Старый ранг остаётся корректной верхней мерой и сохраняет монотонность вдоль parent. Пересчёт дорог и не нужен для границы.

7. Выполните полное сжатие пути для $[0,0,1,2,3,4]$ из вершины 5.

Показать подсказку

Корень равен 0; перепишите родителей всех промежуточных вершин.

Показать решение

Получится $[0,0,0,0,0,0]$. Ребро вершины 1 уже вело к корню и фактически не меняется.

8. Чем path splitting отличается от halving?

Показать подсказку

Сравните, куда переходит текущий указатель после записи дедушки.

Показать решение

Splitting продолжает со старого родителя и переписывает каждую посещённую вершину; halving продолжает с нового родителя и пропускает примерно половину вершин.

9. Является ли $O(\alpha(n))$ границей каждого FIND?

Показать подсказку

Вспомните различие worst-case и amortized.

Показать решение

Нет. Один FIND может пройти логарифмический путь; обратная функция Аккермана ограничивает среднюю цену по допустимой последовательности операций.

10. Как DSU обнаруживает цикл в Краскале?

Показать подсказку

Сравните представителей концов очередного ребра.

Показать решение

Одинаковые представители означают уже существующий путь между концами, поэтому добавление ребра замкнёт цикл. Разные компоненты можно безопасно объединить.

11. Почему обычный DSU не поддерживает удаление ребра?

Показать подсказку

Какие сведения об исходных рёбрах остаются после UNION?

Показать решение

Структура хранит только разбиение и теряет внутренние рёбра. По нему нельзя понять, было удалённое ребро мостом или имело обходной путь.

12. Почему rollback DSU часто отказывается от path compression?

Показать подсказку

Посчитайте число изменений parent, которые пришлось бы записать для отмены.

Показать решение

Compression делает много побочных записей на одном FIND. Без него один union меняет постоянное число ячеек, которые легко сохранить в стеке; size гарантирует логарифмическую глубину.
