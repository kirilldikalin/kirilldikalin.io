Диапазон — это запрос к семейству подмножеств

Дан массив $a_0,\dots,a_{n-1}$. Запрос выбирает полуинтервал $[l,r)$ и просит агрегат: сумму, минимум, максимум, gcd или более сложное состояние. Обновление может менять одну позицию, прибавлять значение на целом диапазоне, присваивать диапазону константу или комбинировать несколько действий. Слово «диапазонная структура» не задаёт одну задачу: интерфейс определяется парой query/update и алгеброй агрегата.

\[ \class{atlas-notation-token notation-id-range-query}{Q(l,r)} =a_l\circ a_{l+1}\circ\cdots\circ a_{r-1}, \qquad 0\le l\le r\le n. \]

Полуинтервал удобен: длина равна $r-l$, соседние $[l,m)$ и $[m,r)$ не пересекаются, пустой диапазон $[l,l)$ естественен. Некоторые структуры и библиотеки используют включительные границы; ошибка на единицу возникает не из дерева, а из смешения контрактов. В этой главе segment tree использует $[l,r)$, а классическая формула Fenwick ниже — индексы $1\dots n$ и включительные префиксы.

Главный вопрос: можно ли представить любой query как объединение небольшого числа заранее поддерживаемых canonical blocks? Prefix sums используют два префикса, sparse table — два перекрывающихся блока для идемпотентной операции, Fenwick — двоичное разложение префикса, segment tree — $O(\log n)$ непересекающихся вершин. Именно это покрытие, а не форма рисунка, выводит сложность.

Нужно также назвать момент ответа. В online-модели операция приходит после предыдущих updates и должна завершиться до следующей. Offline-алгоритм видит весь список запросов, может сортировать их по координате или времени и применять более дешёвый sweep. Persistent query добавляет номер версии. Одинаковая фраза «сумма на отрезке» поэтому может требовать совершенно разных структур.

Для нескольких параметров размер входа — не только $n$. Пусть есть $q$ запросов; total time имеет вид preprocessing $P(n)$ плюс $q\,T_q(n)$ и updates. Структура с дорогой подготовкой окупается лишь при достаточном $q$. Если query возвращает все $k$ подходящих объектов, к оценке добавляется неизбежное $\Omega(k)$ на вывод.

Префиксные суммы: immutable массив обрабатывается один раз

Определим $P_0=0$ и $P_{i+1}=P_i+a_i$. Тогда сумма полуинтервала получается вычитанием:

\[ P_k=\sum_{i=0}^{k-1}a_i, \qquad \sum_{i=l}^{r-1}a_i=P_r-P_l. \]

Построение выполняет $n$ сложений и занимает $O(n)$ дополнительной памяти, каждый query — $O(1)$. Корректность следует из разбиения префикса $[0,r)$ на непересекающиеся $[0,l)$ и $[l,r)$. Метод использует обратимость сложения: вклад левого префикса можно вычесть. Для минимумов формула `min(prefix r) − min(prefix l)` не имеет смысла.

Point update $a_i\mathrel{+}=\Delta$ меняет все $P_{i+1},\dots,P_n$, то есть стоит $\Theta(n)$ при явном массиве префиксов. Если updates отсутствуют или выполняются большой редкой пачкой с последующей перестройкой, это может быть лучшим решением: минимальные константы, последовательная память, простая векторизация. Нельзя выбирать дерево только потому, что его asymptotic query выглядит «умнее».

Переполнение — часть корректности. Сумма $n$ 32-битных значений может не помещаться в 32 бита. Тип префикса выбирают по максимальному модулю и длине; в modular задаче явно суммируют по модулю. Floating-point prefix sums быстры, но вычитание близких больших префиксов может потерять точность.

Двумерный prefix array расширяет идею включением–исключением. Для прямоугольника $[x_1,x_2)\times[y_1,y_2)$ берут четыре угловых префикса: два прибавляют и два вычитают. Построение и память $O(nm)$, query $O(1)$. В больших разреженных координатах плотная таблица неприемлема; тогда coordinate compression и двумерные деревья меняют модель памяти.

Префиксы можно строить для любого группового агрегата: xor использует xor повторно как обратную операцию, векторные суммы вычитаются покоординатно. Для произведения над ненулевыми числами обратимость зависит от области; наличие нулей ломает простое деление префиксов. Структуру выбирают по математическим свойствам данных, а не по знакомому шаблону.

Разностный массив меняет роли query и update

Пусть $D_0=a_0$, $D_i=a_i-a_{i-1}$ для $i>0$. Значение восстанавливается префиксом: $a_i=\sum_{j=0}^{i}D_j$. Чтобы прибавить $\Delta$ всем элементам $[l,r)$, достаточно изменить две границы:

\[ D_l\mathrel{+}=\Delta, \qquad D_r\mathrel{-}=\Delta\quad\text{при }r<n. \]

Внутри диапазона соседние разности не меняются: оба элемента увеличились одинаково. На входе возникает скачок $+\Delta$, после выхода — $-\Delta$. Update стоит $O(1)$, но получение одной точки после многих updates требует префикса $O(n)$ без дополнительной структуры. Если все обновления известны заранее, один финальный проход материализует массив за $O(n+q)$.

Difference array показывает важный принцип: иногда следует хранить не сами значения, а производную, в которой дорогая операция становится локальной. Fenwick над $D$ поддерживает online range-add/point-query за $O(\log n)$. Два Fenwick позволяют range-add/range-sum, но формулы зависят от индексации и должны быть выведены, а не скопированы вслепую.

Вывод двух Fenwick начинается с вклада одного update $+\Delta$ на $[l,r]$ в префикс позиции $x$. Он равен нулю до $l$, затем $\Delta(x-l+1)$ до $r$, после чего остаётся константой $\Delta(r-l+1)$. Это кусочно-линейная функция $x\,B_1(x)-B_2(x)$; один BIT хранит коэффициент при $x$, второй — свободный член. Такой вывод сразу показывает знаки на границах и предотвращает off-by-one.

Ассоциативность позволяет склеивать блоки

Segment tree требует моноид: ассоциативную операцию $\circ$ и нейтральный элемент $e$. Тогда агрегат пустого диапазона равен $e$, а любой набор непересекающихся blocks можно объединять в любом расставлении скобок. Коммутативность не обязательна: для конкатенации строк или матриц порядок блоков нужно сохранять.

\[ (x\circ y)\circ z=x\circ(y\circ z), \qquad e\circ x=x\circ e=x. \]

Prefix difference требует более сильную структуру — обратимый элемент, как в группе. Sparse table с двумя перекрывающимися блоками требует идемпотентность $x\circ x=x$, иначе overlap посчитается дважды. Lazy propagation требует ещё действия обновлений на агрегатах: нужно уметь применить update ко всему segment summary и композиционно объединить несколько pending updates.

Эти требования объясняют различия возможностей лучше таблицы сложностей. `min` ассоциативен и идемпотентен, но не имеет обратной операции; сумма ассоциативна и обратима, но не идемпотентна; присваивание диапазона образует некоммутативную композицию updates, где новое присваивание перекрывает старое.

Для lazy tree полезно мыслить гомоморфизмом: aggregate объединения двух segments получается из aggregates частей, а update действует на aggregate согласованно с объединением. Если $A$ — action, требуется $A(x\circ y)=A(x)\circ A(y)$ с учётом длины, когда summary — сумма. Без этого нельзя обновить целую вершину, не открывая её детей. Например, операция «заменить каждый элемент его квадратом» не определяется только старой суммой; понадобится более богатый summary или спуск к листьям.

Sparse table хранит степени двойки для неизменяемого массива

Таблица $T[k][i]$ хранит агрегат блока длины $2^k$, начинающегося в $i$. Строка $k=0$ — исходные элементы. Следующая строка склеивается из двух половин:

\[ T[k][i]=T[k-1][i]\circ T[k-1][i+2^{k-1}]. \]

Есть $\lfloor\log_2n\rfloor+1$ уровней и $O(n\log n)$ entries. Построение имеет ту же временную и пространственную сложность. Любой диапазон можно разложить на $O(\log n)$ непересекающихся степенных блоков, поэтому для общего моноида query стоит $O(\log n)$.

Для идемпотентного RMQ достаточно двух блоков длины $2^k$, где $k=\lfloor\log_2(r-l)\rfloor$: один начинается в $l$, другой заканчивается в $r$. Они покрывают диапазон и могут перекрываться; повторные элементы не меняют минимум. Query становится $O(1)$. Любой point update потенциально меняет $O(n)$ blocks разных начал, поэтому sparse table предназначена для static data.

Значения $\lfloor\log_2len\rfloor$ можно предварительно вычислить для всех длин за $O(n)$ либо получать битовой операцией `floor_log2`. Таблица уровней хранится последовательно: при построении строки $k$ читаются две области строки $k-1$. На практике $O(n\log n)$ памяти быстро становится ограничением; для 10 миллионов 64-битных значений двадцать четыре уровня занимают около 1,9 ГиБ без overhead.

Disjoint sparse table поддерживает $O(1)$ query для общего ассоциативного агрегата без идемпотентности, заранее храня префиксы и suffix вокруг границ dyadic blocks. Но обновлений по-прежнему нет, память $O(n\log n)$, а реализация сложнее. Это подчёркивает: $O(1)$ static query не принадлежит исключительно `min`, но достигается иной декомпозицией.

RMQ показывает разницу между удобной и предельной структурой

Range Minimum Query просит индекс или значение минимума на диапазоне. Sparse table даёт простое $O(1)$ query после $O(n\log n)$ preprocessing. Существуют структуры с $O(n)$ preprocessing и $O(1)$ query: массив сводится к LCA в декартовом дереве, глубины обхода разбиваются на маленькие типы blocks, ответы внутри типа табулируются, а между blocks используется компактная структура.

Такой результат важен как граница возможного, но не всегда как практический выбор. Константы и сложность реализации могут проигрывать sparse table на умеренном $n$. Если нужны updates, static RMQ вообще перестаёт соответствовать интерфейсу и возвращается segment tree. Алгоритмическая оптимальность относится к точно заданной модели операций.

При равных минимумах интерфейс должен определить, какой индекс вернуть: левый, правый или любой. Значение минимума не различает варианты, а argmin — различает. Агрегат segment tree можно хранить парой `(value,index)` с лексикографическим правилом, сохраняя ассоциативность.

Связь с LCA строится через Euler tour дерева: выписываются посещённые вершины и их глубины, а LCA двух вершин соответствует позиции минимальной глубины между их первыми появлениями. В обратную сторону декартово дерево массива превращает RMQ в LCA. Эти сведения позволяют переносить оптимальные структуры, но требуют $O(n)$ построения и аккуратного tie-breaking.

Fenwick tree кодирует правый конец блока в битах

Binary indexed tree — массив $BIT[1..n]$. Ячейка с индексом $i$ хранит сумму диапазона, который заканчивается в $i$ и имеет длину младшего установленного бита:

\[ \class{atlas-notation-token notation-id-range-lowbit}{\operatorname{lowbit}(i)}=i\mathbin{\&}(-i), \qquad BIT[i]=\sum_{j=i-\operatorname{lowbit}(i)+1}^{i}a_j. \]

В дополнительном коде операция `i & -i` оставляет самый правый единичный бит. Например, $12=1100_2$, поэтому $lowbit(12)=0100_2=4$, а $BIT[12]$ отвечает за индексы 9…12. Индекс 8 имеет lowbit 8 и хранит весь префикс 1…8. Это не явное дерево с указателями, а система вложенных dyadic blocks в плотном массиве.

Для нулевого индекса lowbit равен нулю и шаг зациклится, поэтому классическая версия использует 1-based indexing. Нулевая реализация возможна с другими битовыми формулами, но смешивать варианты нельзя. Плотный layout требует $n+1$ чисел, хорошо использует cache и обычно имеет меньшую константу, чем segment tree.

Блоки Fenwick не образуют разбиение всего массива на одном уровне. Они перекрываются между разными индексами, но конкретный prefix выбирает непересекающуюся цепочку. Например, $BIT[8]$ содержит 1…8, а $BIT[12]$ — 9…12; prefix 13 добавляет ещё $BIT[13]$. Битовое представление правого конца кодирует именно эту цепочку ancestors.

Fenwick можно использовать для frequency table и поиска k-й порядковой статистики. Если frequencies неотрицательны, двоичный lifting по внутренним blocks находит минимальный индекс с prefix sum не меньше $k$ за $O(\log n)$. Обычный бинарный поиск с каждым prefix query стоил бы $O(\log^2n)$. Неотрицательность нужна для монотонности префикса.

Префикс удаляет биты, update добавляет их

Чтобы вычислить prefix $(1..i)$, прибавляем $BIT[i]$ и заменяем $i\leftarrow i-lowbit(i)$. Выбранный block заканчивается в старом $i$, следующий заканчивается перед его началом. Blocks не пересекаются и в сумме покрывают весь префикс. Каждый шаг удаляет один установленный бит, поэтому их не больше $\lfloor\log_2n\rfloor+1$.

Point update позиции $i$ должен изменить все canonical blocks, содержащие её. После изменения $BIT[i]$ переходим $i\leftarrow i+lowbit(i)$. Новый индекс — ближайший предок в неявном дереве; его block расширяется влево и содержит исходную позицию. Каждый шаг увеличивает индекс и добавляет один значимый бит, поэтому updates также $O(\log n)$.

\[ \operatorname{sum}(l,r)=\operatorname{prefix}(r)-\operatorname{prefix}(l-1) \quad\text{для включительных 1-based границ}. \]

Build через $n$ отдельных updates стоит $O(n\log n)$, но возможен линейный build: после записи текущей ячейки её сумму один раз передают непосредственному parent $i+lowbit(i)$. Каждый индекс участвует в постоянном числе действий. Корректность следует из того же отношения containment blocks.

Update и query касаются разных цепочек: query очищает единицы справа налево, update переходит к индексам, blocks которых поглощают текущий. Обе длины логарифмичны, но число cache lines зависит от patterns индексов. На большой памяти jumps не последовательны; всё же компактность одного массива часто делает Fenwick быстрее универсального дерева для сумм.

Segment tree хранит агрегат каждого узла разбиения

Корень отвечает за $[0,n)$, внутренний узел $[l,r)$ делится в $m=\lfloor(l+r)/2\rfloor$ на $[l,m)$ и $[m,r)$, листья — единичные диапазоны. Значение родителя равно композиции детей. Высота $\lceil\log_2n\rceil$, число фактических узлов меньше $2n$ у полного рекурсивного дерева и обычно размещается в массиве константного размера около $4n$ либо в компактном iterative layout $2S$, где $S$ — следующая степень двойки.

Query $[q_l,q_r)$ рассматривает три случая. Нет пересечения — вернуть identity. Полное покрытие — взять сохранённый агрегат, не спускаясь. Частичное пересечение — запросить обоих детей и объединить ответы. На каждом уровне только две пограничные ветви продолжают частичное пересечение; между ними целые blocks уже взяты. Поэтому посещается $O(\log n)$ canonical nodes.

Point update меняет один лист и пересчитывает ancestors до корня, тоже $O(\log n)$. Build снизу объединяет каждый внутренний узел один раз и стоит $O(n)$, не $O(n\log n)$. Пространство $O(n)$. В отличие от Fenwick, операция может быть любым моноидом, а не только удобной обратимой префиксной суммой.

Почему query посещает логарифмическое число взятых узлов, хотя рекурсивный код выглядит ветвящимся? На каждом уровне диапазон запроса пересекает последовательность segments. Все центральные segments покрыты полностью и останавливаются; только segment, содержащий левую границу, и segment, содержащий правую, могут быть частичными. Значит, на уровень продолжаются не более двух пограничных цепочек, а число добавленных siblings также константно.

Segment tree легко аугментировать: для maximum subarray summary хранит total sum, лучший prefix, suffix и внутренний ответ; merge выводит новые четыре поля из детей. Для balanced brackets хранят unmatched opens/closes. Но для каждого summary нужно доказать достаточность: два разных segments с одинаковым summary должны быть неразличимы для любого будущего merge.

Рекурсивный и iterative layout реализуют одно разбиение

В heap-like layout дети узла $v$ имеют индексы $2v$ и $2v+1$. Он прост для рекурсивных диапазонов произвольного $n$, но массив размера $4n$ оставляет holes. Если дополнить листья до степени двойки $S$, их кладут в позиции $S\dots2S-1$, родителей строят снизу. Iterative query двигает две границы вверх и забирает узел, когда граница является правым или левым ребёнком.

Для некоммутативного моноида левый и правый аккумуляторы ведут отдельно: блоки, снятые с левой границы, добавляются справа к левому результату, снятые с правой — слева к правому. В конце вычисляют `left ∘ right`. Наивное сложение blocks в порядке посещения нарушит конкатенацию или матричное произведение.

Рекурсивная версия естественно поддерживает lazy propagation и сложные node summaries. Iterative обычно компактнее и быстрее на point update/range query. Выбор layout не меняет асимптотику, но меняет индексацию, memory footprint, удобство SIMD и риск ошибок.

При $n$, не равном степени двойки, layout $2n$ без padding тоже возможен, но порядок листьев и родителей менее очевиден для некоммутативных queries. Padding нейтральными элементами упрощает доказательство: дополнительные листья не меняют агрегат. Нейтральный элемент должен существовать и быть представлен без переполнения, например $+\infty$ для minimum.

Lazy propagation откладывает одинаковую работу целого сегмента

Range-add наивно меняет каждый лист и стоит $\Theta(r-l)$. Если узел целиком покрыт update, можно сразу изменить его summary и сохранить pending tag, не спускаясь. Для суммы прибавка $\Delta$ на segment длины $len$ меняет значение на $\Delta\cdot len$. Tag означает: логические значения всех листьев уже обновлены, но изменения ещё не материализованы в детях.

\[ sum(v)\leftarrow sum(v)+\Delta\cdot len(v), \qquad \class{atlas-notation-token notation-id-lazy-tag}{lazy(v)}\leftarrow lazy(v)+\Delta. \]

Перед частичным спуском выполняют `push`: применяют tag к обоим детям и очищают его у родителя. После изменения детей выполняют `pull`: пересчитывают summary родителя. Полностью покрытый query может использовать summary без push, потому что он уже отражает update. Так range update и range query посещают только $O(\log n)$ пограничных узлов и canonical cover.

Для range assignment композиция иная: новое присваивание заменяет старое, а последующая прибавка изменяет assigned value. Когда поддерживаются несколько видов updates, tag становится функцией состояния, а композиция имеет порядок. Нужно определить identity update, `compose(new,old)` и `apply(tag,aggregate,len)`. Ошибка порядка даёт правдоподобные, но неверные ответы после смешанной последовательности.

Range minimum с range add проще суммы: прибавка $\Delta$ меняет minimum узла на $+\Delta$ независимо от длины. Range assignment меняет minimum на assigned value. Для range chmin вместе с sum одного обычного lazy tag недостаточно: update затрагивает только элементы выше порога. Segment tree beats хранит maximum, второй maximum и количество maximum, чтобы иногда применить update целиком; его амортизированный анализ значительно сложнее.

Tags экономят время, но не обязаны немедленно доходить до листьев. Поэтому просмотр внутреннего массива дерева без учёта ancestors покажет «устаревшие» leaf values. Публичный интерфейс должен обращаться через query или предварительно push весь путь. Debug-визуализация обязана различать логическое значение и физически материализованное состояние.

Инвариант lazy отделяет логическое значение от материализации

Для каждого узла $v$ храним инвариант: `sum(v)` равен истинной сумме всего его диапазона после всех updates, включая pending tag; значения детей могут не учитывать tag $v$, пока к ним не спускаются. При полном покрытии `apply` меняет summary на точный вклад update и композиционно добавляет tag, поэтому инвариант сохраняется без посещения листьев.

При частичном пересечении summary детей нужно сделать согласованными. `push` переносит действие родителя к каждому ребёнку. Объединение их диапазонов ровно даёт диапазон родителя, поэтому после применения тега сумма детей соответствует прежнему `sum(v)`. Затем рекурсивный update сохраняет инвариант детей, а `pull` восстанавливает равенство родителя их композиции.

Завершимость следует из уменьшения длины сегмента при рекурсивном спуске; лист — база. Сложность $O(\log n)$ для одной интервальной операции выводится из canonical decomposition: полностью покрытые внутренние blocks останавливают рекурсию, частичными остаются только узлы около двух границ. Если update нельзя применить к aggregate за $O(1)$, эта оценка не выполняется.

Тестировать lazy нужно не только случайными итоговыми queries. Полезно сравнивать каждую операцию с маленьким наивным массивом, чередовать полные и вложенные диапазоны, использовать отрицательные updates, пустые границы и длину один. Эти случаи заставляют `push`, `compose` и `pull` взаимодействовать в разном порядке.

Coordinate compression сохраняет порядок, а не расстояния

Если координаты достигают $10^{18}$, но в input встречается только $m$ значений, сортируем уникальные координаты и заменяем каждую её rank от 0 до $m-1$. Fenwick или segment tree строятся на $m$, поэтому память зависит от числа событий, а не величины координаты. Сравнения и порядок сохраняются.

Расстояния не сохраняются. Между координатами 5 и 100 rank отличается на один, но геометрическая длина равна 95. Для задач о длине покрытия нужно хранить исходные gaps и умножать count на физическую длину segment. Для открытых/закрытых концов иногда добавляют соседние sentinel coordinates или сжимают elementary intervals, а не точки.

Online compression сложнее: новый ключ между существующими ranks сдвигает индексы. Тогда используют ordered tree, dynamic segment tree по большому universe или заранее собирают все координаты offline. Слово «compression» не означает lossless encoding значений; это перенумерация релевантного порядка.

При sweep line часто добавляют обе границы interval и соседние координаты, чтобы различать касание и промежуток. Если структура считает покрытую длину, leaf соответствует elementary interval $[x_i,x_{i+1})$ и хранит его реальную длину. Если структура считает число событий в точках, leaf соответствует самой координате. Эти две compression-модели нельзя подменять.

Таблица неполна без типа операции. Sparse table даёт $O(1)$ только в идемпотентном overlap-варианте; Fenwick range sum использует обратимость; lazy segment tree требует корректного действия updates на summary. Константы различаются: prefix array — один cache-friendly subtraction, Fenwick — короткий битовый цикл, segment tree — больше памяти и ветвлений, но гораздо шире интерфейс.

Если запросы известны offline, возможны сортировка событий, sweep line, Mo's algorithm или divide-and-conquer. Онлайн-структура платит за готовность отвечать после каждого update. Нельзя сравнивать их, не сообщая, допустима ли перестановка запросов и когда нужен ответ.

Для immutable sum prefix array доминирует дерево и по времени, и по памяти overhead. Для dynamic sum Fenwick обычно предпочтителен, пока не нужны arbitrary ranges updates или сложный aggregate. Segment tree выбирают за расширяемость и чёткий моноидный контракт. Sparse table — за массив static RMQ с огромным числом запросов. Difference array — за пакет range updates перед единственной materialization.

Можно сочетать структуры. Heavy-light decomposition превращает path query на дереве в несколько ranges базового массива и использует segment tree. Sweep line кладёт активные события в Fenwick. Persistent segment tree отвечает по старым версиям. Структура диапазона часто является внутренним механизмом более крупного алгоритма, поэтому её интерфейс должен соответствовать внешней декомпозиции.

Память, cache и цена универсальности

Prefix и Fenwick используют плотные массивы, мало метаданных и предсказуемые циклы. Segment tree хранит несколько summaries на элемент; объектный узел с pointers добавит allocator overhead и cache misses, поэтому статический размер обычно размещают в массиве. Dynamic segment tree создаёт только посещённые узлы большого universe, но платит указателями и худшей локальностью.

Summary может быть крупным: матрица, top-k кандидаты, несколько статистик. Тогда $O(n)$ nodes означает существенную память, а merge перестаёт быть дешёвой константой. Оценку нужно писать как $O(\log n\cdot C_{merge})$. При range updates стоимость `apply` также зависит от представления action.

Параллельные queries по immutable tree читают общие данные безопасно, updates требуют синхронизации или версий. False sharing возникает, если разные threads меняют соседние entries массива дерева. Персистентный segment tree копирует $O(\log n)$ узлов на update и сохраняет старые версии; это тема отдельной ветви 3.11.

Benchmark включает реальные proportions query/update, распределение длин диапазонов, размер aggregate и warm cache. На коротких массивах простой цикл может выиграть у любого дерева. Асимптотика объясняет рост, но точка пересечения зависит от железа и реализации.

Границы входа влияют на рекурсию и allocation. При $n=0$ identity может дать корректный пустой query, но build без корня требует отдельной ветки. Огромное $n$ способно переполнить `2*S`, даже если сами значения малы. В языках с фиксированным integer size индексы дерева проверяют до выделения памяти, а не после частично построенного массива.

Проверка производительности отделяется от проверки правильности. Сначала property tests сравнивают случайную короткую последовательность с наивным массивом и фиксируют seed падения. Затем benchmark отключает assertions, прогревает runtime и сообщает workload. Быстрый ответ, полученный из неверно скомпонованных lazy tags, не является оптимизацией.

Сериализация дерева тоже требует контракта. Для пересоздаваемого индекса часто достаточно сохранить исходный массив и заново выполнить линейный build. Если сохраняются внутренние nodes и tags, формат должен фиксировать layout, размер типа, identity и порядок композиции. Незавершённый pending tag не является ошибкой: это полноценная часть логического состояния, которую нельзя потерять при восстановлении.

Наблюдаемость помогает ловить деградацию: считают число посещённых nodes, долю полных покрытий, число push и размер summaries. Если range query неожиданно посещает линейно много узлов, чаще нарушен контракт границ или canonical-stop, а не «неудачно сбалансировано дерево»: segment tree имеет фиксированную форму. Эти счётчики связывают доказанную оценку с конкретной реализацией.

Типичные ошибки

  • Смешивать включительные и полуоткрытые границы
  • Вызывать `lowbit(0)` в 1-based Fenwick и получать бесконечный цикл
  • Вычитать префиксные минимумы, будто `min` имеет обратную операцию
  • Использовать overlap sparse table для суммы и считать элементы дважды
  • Забывать `push` перед частичным спуском lazy tree
  • Компоновать assignment и addition tags в неверном порядке
  • Считать recursive build segment tree равным $O(n\log n)$
  • Терять порядок blocks для некоммутативного моноида
  • После coordinate compression использовать rank как физическую длину
  • Обещать $O(\log n)$, хотя merge крупного summary не константен

Лаборатория: покрытие видно геометрически

В режиме Fenwick включительный диапазон разлагается на двоичные префиксные blocks, рядом подписаны lowbit и частичная сумма. Segment tree подсвечивает непересекающиеся covering nodes. Режим lazy update показывает, где прибавка сохраняется целиком и когда pending tag передаётся детям. Числа, формула и SVG строятся из одного состояния ядра.

Упражнения

1. Постройте префиксы массива $[3,-1,4,2]$ и найдите сумму $[1,4)$.

Подсказка

Начните с $P_0=0$.

Показать решение

$P=[0,3,2,6,8]$, ответ $P_4-P_1=8-3=5$.

2. Запишите изменения difference array для прибавки 7 на $[2,6)$.

Подсказка

Меняются только границы.

Показать решение

$D_2\mathrel{+}=7$, $D_6\mathrel{-}=7$, если индекс 6 существует.

3. Почему два перекрывающихся sparse blocks корректны для `min`, но не для `sum`?

Подсказка

Сравните $\min(x,x)$ и $x+x$.

Показать решение

Минимум идемпотентен, повтор элемента не меняет результат. В сумме overlap учитывается дважды.

4. Какие индексы посещает prefix Fenwick от $i=13$?

Подсказка

Последовательно вычитайте lowbit.

Показать решение

$13\to12\to8\to0$; blocks $[13,13]$, $[9,12]$, $[1,8]$ покрывают префикс.

5. Докажите, что Fenwick prefix делает не более числа битов индекса шагов.

Подсказка

Что происходит с младшей единицей?

Показать решение

$i-lowbit(i)$ удаляет ровно младший установленный бит. Шагов равно popcount$(i)\le\lfloor\log_2i\rfloor+1$.

6. Разложите segment query $[2,7)$ над восемью листьями на canonical nodes.

Подсказка

Берите крупнейшие dyadic blocks внутри диапазона.

Показать решение

Возможное покрытие: $[2,4)\cup[4,6)\cup[6,7)$. Blocks непересекаются и покрывают запрос точно.

7. Почему build segment tree имеет линейное число merge?

Подсказка

Посчитайте внутренние узлы полного бинарного дерева.

Показать решение

У дерева с $S$ листьями $S-1$ внутренних узлов. Каждый merge выполняется один раз, итого $O(S)=O(n)$ после дополнения до степени двойки.

8. После range-add $+3$ на узле длины 5 как меняются sum и lazy?

Подсказка

Все пять листьев логически увеличились.

Показать решение

$sum\mathrel{+}=15$, $lazy\mathrel{+}=3$; дети пока могут оставаться нематериализованными.

9. Новое assignment `=4` приходит после pending add `+2`. Как скомпоновать tags?

Подсказка

Присваивание уничтожает прежнее значение.

Показать решение

Новый tag — assignment 4 без старой прибавки. Если порядок обратный, assignment 4 затем add 2 дают assignment 6. Композиция некоммутативна.

10. Координаты $[5,100,1000]$ сжаты в $[0,1,2]$. Какова физическая длина промежутка ranks 0…1?

Подсказка

Вернитесь к исходным значениям.

Показать решение

$100-5=95$, а не 1. Rank сохраняет порядок, но не расстояние.

11. Выберите структуру для миллиона static RMQ и объясните компромисс.

Подсказка

Сравните sparse table и линейное RMQ.

Показать решение

Sparse table проста и даёт $O(1)$ query, но требует $O(n\log n)$ памяти. Fischer–Heun достигает $O(n)$ памяти и preprocessing, но сложнее и может проиграть константами. Выбор зависит от memory budget и объёма запросов.
