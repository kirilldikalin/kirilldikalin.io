Строка раскрывается в последовательность решений

Словарь обычно сравнивает ключи целиком: хеш-таблица вычисляет hash всей строки, дерево многократно выполняет лексикографическое сравнение. Trie рассматривает ключ $c_1c_2\dots c_m$ как путь по рёбрам $c_1,c_2,\dots,c_m$. Все слова с общим префиксом проходят через одну вершину. Поэтому поиск зависит прежде всего от длины ключа, а prefix query превращается в обычный спуск к вершине.

Пусть в словаре есть «дом», «дома» и «домен». Путь д→о→м общий. Вершина после «м» одновременно отмечает конец «дом» и имеет потомков. Отдельный terminal flag принципиален: наличие пути доказывает существование префикса, но не полного ключа. Без флага структура ошибочно объявит «до» словом или не сможет хранить ключ, являющийся префиксом другого.

Цифровой поиск

Эдвард Фредкин в статье «Trie Memory» описал память, адресуемую последовательными частями аргумента. Название trie связано с retrieval и обычно произносится так, чтобы отличать его от tree. Позднее PATRICIA Дональда Моррисона сжала неразветвляющиеся пути.

Инвариант: путь однозначно кодирует префикс

Корень соответствует пустой строке $\varepsilon$. Из каждой вершины выходит не более одного ребра с данным символом. Строка, прочитанная вдоль пути от корня к вершине $v$, — её префикс $pref(v)$. Вершина terminal тогда и только тогда, когда $pref(v)$ принадлежит хранимому множеству ключей. Этот инвариант определяет семантику независимо от способа хранения детей.

\[ pref(root)=\varepsilon, \qquad pref(child)=pref(parent)\cdot label(parent,child). \]

В обычном trie label — один символ. Под «символом» реализация должна понимать конкретную единицу: byte, Unicode code point, grapheme cluster, token или bit. Оценка длины и равенство зависят от этого решения. Нормализация NFC/NFD, регистр и локаль относятся к контракту ключа до вставки; два визуально одинаковых текста могут иметь разные code points.

Из инварианта следует корректность membership. Если на очередном символе нет ребра, ни один сохранённый ключ с уже совпавшим префиксом не может продолжаться нужным символом. Если весь input прочитан, ответом служит terminal flag достигнутой вершины.

Вставка создаёт только отсутствующий suffix

Вставка проходит существующий longest common prefix. При первом отсутствующем ребре создаётся цепочка для оставшегося suffix, а последняя вершина помечается terminal. Все прежние пути сохраняются; новый путь читает ровно вставленный ключ. Если путь существовал целиком, меняется только terminal: это отличает добавление «дом» после «дома» от дубликата.

Удаление сначала снимает terminal. Затем можно подниматься к корню и удалять вершины, которые не terminal и не имеют детей. Остановиться нужно при первом branching или terminal: такая вершина участвует в другом ключе. Корректность prune следует из того, что удаляемый suffix больше не лежит ни на одном пути сохранённого слова.

В radix tree после prune может возникнуть нетерминальная вершина с единственным ребёнком. Её labels склеивают повторно. Если удалённый key находился внутри общего пути, terminal снимается, но вершина сохраняется, пока имеет несколько детей. Таким образом, deletion состоит из трёх отдельных обязательств: удалить ровно membership mark, убрать недостижимые листья и восстановить maximal path compression, не проходя через terminal boundary.

Enumeration выполняет DFS от нужной вершины, дописывая labels. Вывод $k$ слов общей длины $L$ требует как минимум $\Omega(L)$ времени на создание результата. Заявление «autocomplete за $O(m)$» описывает только нахождение вершины prefix, но скрывает стоимость выдачи. Top-k подсказки можно аугментировать рейтингами, однако update обязан поддерживать их по всему пути.

Время выражается через длину ключа

Если переход к ребёнку стоит $C_{child}$, поиск ключа длины $m$ занимает $O(mC_{child})$. При dense array потомков $C_{child}=O(1)$ в RAM-модели; при sorted vector — $O(\log d)$ сравнений для степени $d$; при хеш-таблице — ожидаемое $O(1)$ с её предположениями. Поэтому короткая запись «trie lookup $O(m)$» включает модель хранения детей.

\[ T_{find}(x)=O\!\left( \class{atlas-notation-token notation-id-trie-key-length}{|x|} \cdot C_{child} \right). \]

Эта оценка не зависит явно от числа ключей $n$, что выгодно при множестве коротких strings. Но $m$ может быть большим; BST выполняет $O(\log n)$ сравнений, каждое потенциально читает общий префикс заново. Реальная граница зависит от distribution префиксов, cache и representation. Нельзя сравнивать $O(m)$ с $O(\log n)$ без связи между $m$ и $n$ и стоимости string comparison.

В radix tree одно ребро содержит несколько символов. Сравнений вершин меньше, но суммарно успешный поиск всё равно проверяет каждый символ ключа не более постоянного числа раз, то есть $O(m)$ при прямом label comparison. Ошибочная реализация, копирующая suffix при каждом спуске, может добавить квадратичную работу; используют offsets или string views.

Большой алфавит делает наивный trie дорогим

Если каждая вершина хранит массив размера $\class{atlas-notation-token notation-id-trie-alphabet-size}{|\Sigma|}$, переход постоянный, но память $O(V|\Sigma|)$, где $V$ — число вершин. Для binary trie это приемлемо; для Unicode — невозможно. Большинство slots пусты, особенно около листьев. Даже массив на 256 bytes/pointers быстро доминирует над самими ключами.

Sparse map хранит только существующие рёбра: linked list экономит память при малой степени, sorted vector компактен и cache-friendly, hash map ускоряет большой branching ожидаемо, balanced tree сохраняет порядок. Hybrid node может менять representation при росте степени. Adaptive radix tree использует несколько размеров node, чтобы плотность и SIMD-поиск соответствовали фактическому branching.

Число вершин не превосходит единицы плюс сумма длин всех ключей, но при слабом sharing близко к этому пределу. Каждая объектная вершина добавляет header, allocator metadata и pointer alignment. Arena allocation и компактные integer offsets уменьшают overhead. Path compression атакует другой источник расходов — длинные unary chains.

Radix tree сжимает неразветвляющиеся пути

Если нетерминальная вершина имеет ровно одного ребёнка, промежуточное решение ничего не различает. Её можно удалить и склеить labels двух рёбер. В compressed trie, или radix tree, label — непустая строка $\class{atlas-notation-token notation-id-radix-edge-label}{\lambda(e)}$, а первые символы исходящих labels одной вершины различны.

\[ pref(child)=pref(parent)\cdot \class{atlas-notation-token notation-id-radix-edge-label}{\lambda(parent,child)}, \qquad |\lambda|\ge1. \]

Поиск выбирает edge по первому символу, затем сравнивает весь label с соответствующим suffix input. Полное совпадение ведёт к ребёнку; расхождение внутри label доказывает отсутствие ключа. При вставке частичного совпадения edge делится: общий prefix становится label до новой branching-вершины, два различных suffix — исходящими рёбрами.

После удаления radix tree снова сжимает нетерминальную вершину с одним ребёнком. Terminal вершину сжимать через границу нельзя: там заканчивается сохранённый ключ. Path compression сохраняет множество путей и terminal positions, но уменьшает число nodes и pointer traversals. Объём символов labels не обязан уменьшиться, особенно если labels копируются; обычно хранят slices исходных key bytes.

Patricia trie хранит только различающие позиции

Историческая PATRICIA ориентирована на binary keys. Вместо узла на каждый bit сохраняются branching positions, где ключи впервые различаются. Внутренний узел сообщает номер проверяемого bit, листья — полные keys или ссылки на records. Неразличающие последовательности bits пропускаются, поэтому число внутренних узлов для $n$ различных keys линейно по $n$.

Patricia часто называют binary radix tree, но конкретные representations различаются: labels могут быть implicit через bit index, а листья подтверждают полное равенство ключа после маршрута. Это важно, потому что compressed path сам по себе может хранить только позицию различия, не все пропущенные bits. Финальная проверка защищает от ложного совпадения.

Insert находит leaf-кандидат, вычисляет первый различающий bit нового и старого ключа, затем вставляет branching node в правильное место возрастающей последовательности bit positions. Correctness опирается на то, что до этой позиции keys равны, а в ней уходят в разные children.

Поиск проверяет bit positions в строго возрастающем порядке. Пропущенные bits не сравниваются на внутренних узлах, поэтому leaf-кандидат обязательно сверяют с полным ключом. Это не лишняя страховка, а часть алгоритма: набор branching tests отделяет существующие leaves друг от друга, но неизвестный ключ способен пройти к ближайшему leaf по тем же различающим позициям.

Префиксный поиск естественен, но выдача не бесплатна

Чтобы найти все keys с prefix $p$, спускаемся по $p$. В обычном trie достигаем вершины; в radix tree input может закончиться внутри edge label, что всё равно определяет поддерево. Затем обходим terminals ниже. Стоимость нахождения $O(|p|)$, полная стоимость $O(|p|+L)$, где $L$ — объём выданных keys или records.

Autocomplete часто требует не все, а top-k. В каждой вершине можно хранить лучшие candidates своего поддерева: query быстрый, но insert, delete и изменение рейтинга обновляют summaries вдоль пути и расходуют память. Альтернатива — best-first traversal с upper bounds. «Trie умеет autocomplete» описывает основу, но ranking — отдельный алгоритмический слой.

Prefix count поддерживается полем числа terminal в поддереве. Оно увеличивается только при новой вставке, уменьшается при настоящем удалении и пересчитывается при split/merge radix edge локально. Как и любая аугментация, поле требует инварианта и tests на дубликатах.

Longest prefix match запоминает последний terminal

В таблице маршрутизации несколько prefixes могут совпадать с адресом, например 10/8 и более специфичный 10.4/16. По правилу longest prefix match выбирают совпавший prefix максимальной длины. Trie проходит bits адреса и запоминает последний terminal с route payload. Если дальнейшее ребро отсутствует, возвращается сохранённый candidate, а не failure.

Для IPv4 длина пути ограничена 32 bits, для IPv6 — 128. Binary trie прост, но требует много pointer accesses; path compression, multi-bit stride и bitmap nodes уменьшают их число. Больший stride увеличивает потенциальное branching и память. Hardware/software routing designs выбирают компромисс между update rate, memory bandwidth и latency.

LPM отличается от обычного membership: terminal на коротком prefix является допустимым fallback даже при несовпадении полного input. Ошибка «проверить terminal только в конце» потеряет default и aggregate routes. Обратный trie по компонентам используется для доменных suffix и путей, но направление обхода является частью контракта.

Например, таблица содержит default route 0/0, 10/8 и 10.4/16. Адрес 10.4.7.9 проходит все три terminal и выбирает /16; 10.8.1.2 останавливается после /8; 192.0.2.1 возвращает default. Если более специфичный путь отсутствует, длинное частичное совпадение без terminal не должно вытеснить последний настоящий route.

Представление children определяет фактические константы

Dense array даёт прямой индекс по символу и хорош при маленьком фиксированном alphabet. Sorted small vector хранит пары (symbol,child) рядом и часто выигрывает до десятков children. Hash map полезна при большом branching, но добавляет load factor, hash и нестабильный порядок. Balanced map даёт worst-case logarithm и ordered enumeration.

Bitmap плюс compact child array — промежуточный вариант: bit сообщает наличие символа, rank среди единиц даёт позицию child. Для alphabet 256 bitmap занимает 32 bytes, а pointers хранятся только для существующих рёбер. Popcount обычно аппаратный. Adaptive node меняет форму по мере роста, но переход между representations должен быть атомарным относительно readers.

Radix label тоже имеет representation: owned string упрощает lifetime, но split копирует; slice (key,offset,length) экономит память, но требует, чтобы backing key жил достаточно долго; interned storage разделяет bytes. Complexity statement должно учитывать сравнение label и allocation policy.

Ternary, adaptive и минимальные автоматы меняют компромисс

Ternary search tree хранит в вершине символ и три ссылки: меньше, равно, больше. Поиск символа внутри уровня ведёт себя как BST, а переход equal продвигает позицию ключа. Память на вершину фиксирована, но стоимость зависит от формы дерева сравнений символов. Структура сохраняет prefix enumeration, однако требует балансировки или хорошего распределения.

Adaptive radix tree выбирает node capacity по фактической степени и может хранить path prefix внутри node. Он стремится уменьшить пустые pointers и число cache misses, оставаясь динамическим ordered index. Directed acyclic word graph или минимальный acyclic finite-state automaton объединяет одинаковые suffix-поддеревья, а не только prefixes. Для статического словаря это сильно экономит память, но incremental update и payload semantics сложнее.

Succinct tries кодируют topology битовыми последовательностями и поддерживают rank/select, приближаясь к информационному пределу. Они особенно важны для огромных read-mostly dictionaries. Все варианты сохраняют одну идею — навигацию по digits ключа, — но дают разные гарантии updates, locality и compression. Поэтому слово trie описывает семейство, а не единственный layout. Перед выбором реализации нужно заранее зафиксировать набор операций, изменяемость словаря, единицу символа, допустимую память, модель угроз и требуемый порядок выдачи результатов.

Trie не заменяет B-tree и хеш-таблицу

Хеш-таблица обслуживает exact match ожидаемо за время hash $O(m)$ и короткий probe, но не сохраняет порядок и не даёт prefix enumeration без дополнительного индекса. Trie тоже читает $m$ символов, разделяет prefixes и поддерживает LPM, но расходует больше metadata и pointer traversals. Для длинных случайных keys sharing мало, и hash может быть компактнее.

B-tree группирует много полных separators на странице, минимизирует external-memory I/O, поддерживает lexicographic range и predecessor. Trie делает шаг по digit и может иметь большую глубину в pages. В memory prefix workloads radix tree привлекателен; на диске B+‑tree или специализированный succinct trie лучше используют blocks.

Строковые автоматы и suffix indexes решают другие задачи. Trie индексирует множество keys от начала. Для поиска pattern внутри одного текста нужны suffix array/tree, automaton или FM-index. Переворот keys превращает suffix query в prefix query, но не делает trie полнотекстовым индексом всех substrings без огромного множества suffix.

Нормализация, локальность и обновления решают исход

До вставки задают canonical encoding. Case folding, Unicode normalization и locale rules могут менять длину и равенство. Если поиск нормализует иначе, путь не совпадёт. Для display сохраняют оригинальный key отдельно, а index строят по canonical form. Изменение правил требует перестройки.

Object-per-character trie часто медленнее ожидаемого из-за cache misses. Arena, packed arrays, breadth-first layout и path compression уменьшают разрозненность. Hot prefixes могут стать contention points при concurrent updates. Lock-free варианты должны решать publication нового edge и безопасное освобождение nodes; последовательный proof этого не покрывает.

Измерение включает distribution длин и общих prefixes, alphabet, долю exact/prefix queries, число результатов и память на key. Набор случайных UUID и словарь естественного языка дают противоположные формы. Одна таблица $O(m)$ не предсказывает memory footprint и cache behavior. Поэтому успешные и неуспешные запросы измеряют раздельно: они могут проходить разное число символов, рёбер и физических страниц.

Типичные ошибки

  • Считать существующий путь доказательством terminal key
  • Не фиксировать, что является символом и как нормализуется Unicode
  • Обещать $O(m)$ при child map с более дорогим lookup и не назвать модель
  • Сжимать через terminal-вершину и терять короткий ключ
  • При split radix edge неверно выделять общий prefix
  • Копировать suffix на каждом шаге и получить лишнюю квадратичную работу
  • Забывать последний terminal в longest prefix match
  • Считать prefix enumeration независимым от размера результата
  • Использовать rank сжатой координаты как длину string label
  • Сравнивать trie с B-tree без модели памяти

Лаборатория: от символов к сжатым рёбрам

Введите от двух до девяти ключей. Пошаговая вставка выделяет уже общий prefix, создаваемое ребро и отдельную terminal-метку. Последний кадр удаляет все нетерминальные unary-вершины и переносит их символы в radix labels. Счётчики показывают число логических символов и фактически хранимых рёбер; большая геометрия агрегируется без обрезания математического состояния.

Упражнения

1. Постройте trie для «кот», «код», «ком» и укажите terminal-вершины.

Подсказка

Первые две буквы общие.

Показать решение

Путь к→о общий, затем три ребра т, д, м; terminal отмечены на концах трёх ветвей.

2. Почему путь «до» в trie слов «дом» и «дома» не означает membership?

Подсказка

Проверьте terminal flag.

Показать решение

Вершина существует как общий prefix, но не terminal. Membership требует и полного пути, и отметки конца.

3. Докажите, что prune после удаления не уничтожает другой ключ.

Подсказка

Когда подъём останавливается?

Показать решение

Удаляются только нетерминальные вершины без детей. Если вершина нужна другому ключу, она либо terminal, либо имеет child, поэтому prune остановится.

4. Сожмите цепочку ключей «roman», «romane», «romanus» в radix tree.

Подсказка

Terminal roman нельзя удалить.

Показать решение

Ребро roman ведёт к terminal-вершине, из неё выходят labels e и us к двум terminal-листьям.

5. Что происходит при вставке «romulus» в edge label roman?

Подсказка

Найдите longest common prefix labels.

Показать решение

Общий prefix rom; edge делится в новой вершине, старый suffix an и новый ulus становятся разными рёбрами.

6. Выведите память dense-child trie для $V$ вершин и alphabet 256 при восьмибайтовом pointer.

Подсказка

Считайте только child arrays.

Показать решение

$V\cdot256\cdot8=2048V$ bytes, без headers и alignment.

7. Почему exact hash lookup не решает longest prefix match?

Подсказка

Длина совпавшего prefix заранее неизвестна.

Показать решение

Нужно проверить несколько возможных длин или дополнительный индекс. Trie проходит bits один раз и запоминает последний terminal.

8. Как получить longest suffix query из prefix trie?

Подсказка

Измените направление ключей.

Показать решение

Хранить перевёрнутые keys и переворачивать query; общий suffix станет общим prefix.

9. Сравните sorted vector и hash map children для степени три.

Подсказка

Учитывайте cache и overhead.

Показать решение

Vector делает до двух сравнений бинарно или три линейно, хранится плотно и обычно дешевле metadata hash table. Hash становится выгоднее при большем branching и подходящей нагрузке.

10. Сформулируйте тест, который ловит ошибочное сжатие terminal-вершины.

Подсказка

Один ключ должен быть префиксом другого.

Показать решение

Вставить «a» и «ab», сжать, затем проверить membership обоих и отсутствие пустого/«abc». Terminal на границе должен сохраниться.
